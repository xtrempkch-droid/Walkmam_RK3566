# Game Console R35S (RK3326) — painel, port e o que falta

Placa nova em preparação: **Game Console R35S** (a mesma base do R36S, vendida
como "Data Frog" e clones). Este documento existe porque essa placa **quebra a
premissa do repositório**: ela não é RK3566.

| Item | Estado |
| --- | --- |
| SoC | **Rockchip RK3326** (família PX30), 4x Cortex-A35, Mali-G31 — **confirmado** nos DTS de referência |
| DTS próprio no mainline | **não existe** (v6.12 tem 6 DTS `rk3326-*`, nenhum é R35S/R36S) |
| Painel | 640x480 DSI 4 lanes; **vários modelos** por lote — números em `devices/game-console-r35s/dts/Readme.md` |
| Overlay de painel | **gerado e validado** contra o overlay oficial `r36s-panel4` (160 strings idênticas) |
| Build no pipeline atual | **impossível**: U-Boot/kernel/blobs são RK3566 |
| Boot em hardware | **nunca testado** |
| Botões / ADC / bateria / Wi-Fi / BT | **não medidos** (nada foi inferido) |

## 1. O que já existia na pasta (antes de mexer)

O diretório `devices/game-console-r35s/` já estava no repositório com:

- `device.config` (nome errado, e o conteúdo era literalmente `1`) — trocado por
  `device.conf`;
- `dts/mipis-panel4.dts` e `dts/mipis-panel4-V22.dts` — **DTBs decompilados** de
  kernel de fabricante, com o painel completo (timings + sequência de init);
- `dts/Readme.md` e `uboot/README.md` vazios.

Ou seja: alguém já tinha ido atrás do **painel**, que é a parte que o R35S tem de
mais chato. Esse material é o que sustenta tudo aqui, e ele mostra, no primeiro
campo, que a placa é `rockchip,rk3326` e `arm,cortex-a35`.

## 2. Por que ela não entra no pipeline atual

O pipeline (`/.github/workflows/build.yml`) baixa U-Boot mainline, kernel v6.12 e
`rkbin`, e compila `powkiddy-x55-rk3566_defconfig` com `rk3568_bl31` +
`rk3566_ddr`. Para o R35S, os três pilares mudam:

| Peça | RK3566 (hoje) | RK3326 (R35S) | Fonte |
| --- | --- | --- | --- |
| Defconfig do U-Boot | `powkiddy-x55-rk3566` | `odroid-go2` (único rk3326 do mainline) | `doc/board/rockchip/rockchip.rst` |
| BL31 | `rk3568_bl31_v1.43.elf` | `px30_bl31_v1.37.elf` (rkbin **não** tem `rk3326_bl31`) | listagem de `rkbin/bin/rk33/` |
| DDR/TPL | `rk3566_ddr_1056MHz_*.bin` | `px30_ddr_333MHz_v2.12.bin` | idem |
| DTS | `rk3566-*.dts` | `rk3326-*.dts` (outro `Kconfig` de plataforma) | `arch/arm64/boot/dts/rockchip/Makefile` do v6.12 |
| Painel | `rocknix,generic-dsi` via DTS da X35S | 6 modelos diferentes → overlay | ver §3 |

Isso não é "ajuste de config": é um segundo alvo de build. Por isso
`device.conf` está com `image_dtb=` vazio (o empacotador recusa a placa em vez de
gerar uma imagem que não liga) e `status=reference-rk3326-needs-separate-pipeline`.

## 3. O painel: por que "escaneia e descobre" não existe (e o que usar)

### 3.1 O que a KNULLI faz (a recomendação que veio no pedido)

Fui ver o repositório da KNULLI. Para o R36S ela tem
`board/batocera/rockchip/rk3326/r36s/`, com kernel **4.4 de fabricante** e o DTB
**fixo** `rk3326-rg351mp-linux.dtb` copiado no boot (`create-boot-script.sh` +
`boot.ini`). Não há detecção de painel: a KNULLI escolheu o DTB da RG351MP
(640x480, mesma família de painel) e é isso.

### 3.2 O que a ROCKNIX/REG Linux (sucessora) faz

A wiki da REG Linux, na seção *New displays (R36s of year 2024)*, manda:

> "Determine which panel do you have (or just try every option until it works)"

e o mecanismo é um **overlay no cartão**: baixar
`mipi-panel.dtbo.r36s-panel*` do release
[`panel_overlays`](https://github.com/stolen/rnix/releases/tag/panel_overlays),
renomear para `overlays/mipi-panel.dtbo` na partição de boot, reiniciar. Os
overlays disponíveis hoje: `r36s-panel1`, `2`, `3`, `4`, `r36s_clone`,
`rg351mp-v2`, `rg351v-v2`, `cb408`.

### 3.3 Resumo honesto

**Nenhum firmware conhecido descobre o painel sozinho.** E não é preguiça: painel
DSI não tem EDID como monitor de PC, e sem driver de painel funcionando não há
como ler um identificador — o próprio driver é que precisa dos timings/init para
ligar a tela. O que existe é:

1. **escolher** (menu / arquivo), ou
2. **tentar as variantes** até uma ligar, ou
3. confiar no lote de fabricação (antes/meados/depois de 2024).

O que este projeto faz é o item 2 de forma organizada (§4).

## 4. Mecanismo adotado: overlay → um DTB por variante → entrada de boot

Reaproveita o que o projeto já usa para X35S/X55 (`extlinux.conf.<placa>` com
outro `FDT`), sem inventar suporte a overlay em tempo de boot:

```
dts/mipis-panel4.dts            <- DTS de fabricante (fonte)
        │  tools/panel_overlay_from_dts.py
        ▼
dts/panel-overlay/mipi-panel.dts   <- overlay rocknix,generic-dsi (gerado)
        │  dtc -@            (dtbo)  ou  fdtoverlay no DTB base
        ▼
dtbs/rk3326-<base>-panel4.dtb      <- uma imagem por variante de painel
        │
        └── extlinux/extlinux.conf.panel4  (FDT=...)
```

A ferramenta nova é `tools/panel_overlay_from_dts.py`. Ela não é chute: o formato
foi reconstruído e **conferido contra o overlay oficial**, e o teste embutido
compara string por string:

```sh
python3 tools/panel_overlay_from_dts.py \
    devices/game-console-r35s/dts/mipis-panel4.dts \
    --check-arquivo mipi-panel.dtbo.r36s-panel4     # -> OK: 160 strings idênticas
```

Três coisas que só apareceram por causa dessa comparação (e que, se feitas "no
olho", dariam tela preta):

1. **flags**: o fabricante usa `0xa03`, o overlay oficial usa **`0xe03`** — o
   driver `generic-dsi` espera o bit `MIPI_DSI_MODE_VIDEO` (0x400) ligado.
2. **`horizontal`/`vertical`**: são *(display, front-porch, sync-len,
   back-porch)*, **não** `hsync_start/hsync_end/htotal`. A tabela antiga em
   `docs/hardware-e-drivers.md` §4.1 está ambígua nesse ponto — os números
   oficiais (`640,46,2,44` para 640/46/2/44) não deixam dúvida.
   → **corrigido lá** (ver §7).
3. **50 Hz / 75 Hz**: no DTS do fabricante os dois estão com os porches do modo
   de 60 Hz (dão 77,4 fps). O overlay oficial recalcula o `vfront-porch` para
   bater no nome do nó. A regra está no script e é a única parte reconstruída com
   **um** ponto de dados — está marcada como hipótese no cabeçalho dele.

## 5. O que o pipeline precisa (checklist para o próximo build RK3326)

Nada disso foi feito — é a lista de trabalho, na ordem:

1. **Novo job/arquivo de workflow para RK3326** (não misturar com o job atual):
   `make odroid-go2_defconfig`, `BL31=px30_bl31_v1.37.elf`,
   `ROCKCHIP_TPL=px30_ddr_333MHz_v2.12.bin`.
2. **Kernel**: `ARCH_PX30`, os drivers de `devices/game-console-r35s/kernel.fragment`
   e o `panel-generic-dsi.c` da ROCKNIX (o CI já sabe buscá-lo — passo
   "Fetch ROCKNIX Config & Patches").
3. **DTB base**: o R35S não tem DTS no mainline. Candidatos, do mais provável ao
   menos, para bring-up:
   `rk3326-anbernic-rg351m` (640x480, `elida,kd35t133`, mesma faixa de hardware
   que a KNULLI escolhe para o R36S) → `rk3326-gameforce-chi` → `rk3326-odroid-go3`.
   **Nenhum é o R35S**: botões e ADC vão precisar de DTS próprio, medido no
   aparelho. Não escrever `gpio-keys` por chute.
4. **Overlay do painel**: compilar `dtc -@` e aplicar com
   `fdtoverlay -i <base>.dtb -o <base>-panel4.dtb mipi-panel.dtbo`, gerando uma
   entrada `extlinux.conf.panel<N>` por variante.
5. **Rotação**: `display_transform` em `device.conf` já é lido pelo
   `build/create-image.sh`; hoje está `normal` (painel 640x480 na horizontal),
   **não medido**.
6. **Rootfs**: igual ao das outras placas (Debian + Kodi/RetroArch). O rootfs não
   depende do SoC.

## 6. Riscos e pontos cegos (o que pode dar errado sem aviso)

| Risco | Por quê | Como detectar |
| --- | --- | --- |
| **Blob de DDR** | o `px30_ddr_333MHz` é do Go Advance; o R35S tem outro lote de memória. Se errar, o U-Boot morre sem print | sem serial, é tela preta sem nada; com serial (`ttyS2`, 1500000n8), nada aparece |
| **Botões/ADC** | DTS base é de outra placa | `evtest` / `/proc/bus/input/devices` |
| **Wi-Fi/BT** | não se sabe se o R35S tem rádio nem qual | `dmesg | grep -iE 'mmc|rtw|hci'`, `rfkill list` |
| **Áudio** | o DTS base usa `rk817-codec`; o R35S deve usar o mesmo, mas o caminho do amplificador é placa | `aplay -l`, `dmesg | grep -i asoc` |
| **TF1/TF2** | o R35S tem dois slots; o Go Advance só um | `lsblk`, `dmesg | grep mmc` |
| **USB-C** | o R35S usa USB-C; papel OTG/UDC desconhecido | `ls /sys/class/udc`, `dmesg | grep -i dwc` |

## 7. Correção de documentação feita junto

`docs/hardware-e-drivers.md` §4.1 dizia que `horizontal`/`vertical` eram
`hdisplay, hsync_start, hsync_end, htotal`. A comparação com o overlay oficial
mostra que o campo é *(display, front-porch, sync-len, back-porch)*. O texto foi
corrigido; os valores da X35S que estão lá continuam válidos (eles já eram
porches, só estavam descritos com o nome errado).

## 8. Próximos passos (na ordem)

1. **Ligar o aparelho com a imagem oficial (ROCKNIX/ArkOS) e medir**, antes de
   escrever qualquer DTS nosso:
   - `cat /proc/device-tree/model` e `cat /proc/device-tree/compatible`;
   - qual DTB a imagem oficial usa (`ls /boot`, `cat /boot/extlinux/extlinux.conf`
     ou `boot.ini`);
   - `ls /sys/bus/iio/devices/` (eixos por ADC), `evtest` (botões),
     `lsblk` (TF1/TF2), `ls /sys/class/udc` (USB), `rfkill list` (rádio).
   Isso responde "qual DTB base" e "quais botões" com fato, não com palpite.
2. Se a tela ficar preta: **é o painel** (não o resto). Trocar a variante
   (`panel1`…`panel4`, `r36s_clone`) até ligar; anotar qual.
3. Só então montar o job RK3326 no CI (checklist §5) e gerar a primeira imagem.
4. Com a imagem no aparelho: `dmesg` completo para `diagnostico.txt`, como já é
   feito nas outras placas.

## 9. CONFIRMADO com os arquivos do aparelho (2026-10-30)

O usuário forneceu o conteúdo real da partição de boot da imagem que **funciona** no
aparelho (ROCKNIX): 5 `extlinux.conf`, 17 `.dtb` e os 5 overlays de painel. Isso
encerra várias hipóteses deste documento.

### 9.1 Qual é a unidade e qual é o painel

O `extlinux.conf` **ativo** no cartão diz:

```text
FDT /rk3326-gameconsole-r36s.dtb
FDTOVERLAYS /overlays/mipi-panel4.dtbo
```

Ou seja: **a unidade é panel4** (a tela "nova"), e não a original `st7703` do DTB
base. Confirmações independentes:

| Verificação | Resultado |
| --- | --- |
| `tools/panel_overlay_from_dts.py --check-arquivo J:\overlays\mipi-panel4.dtbo` | **160 strings idênticas** — o overlay que o projeto gera é o mesmo que liga a tela |
| `rk3326-r35s-linux.dtb` (vendor "fix by lxc") tem `panel-init-sequence` de **773 bytes / 155 passos** começando em `15 00 02 ff 30` | é exatamente o mesmo painel do overlay4 (155 passos) e do `mipis-panel4.dts` que já estava no repositório |
| `dsi,flags = 0x0a03` no vendor | igual ao que convertemos para `0xe03` |

### 9.2 `FDTOVERLAYS` existe no U-Boot que o projeto fixa

`include/pxe_utils.h` no commit fixado (`0a55b098d6f5f6bafa84fc2f18b433dd167bf729`)
tem `char *fdtoverlays;` em `struct pxe_label` — **o parser de extlinux do nosso
U-Boot aceita `FDTOVERLAYS`**. Isso muda a arquitetura do port:

* **não** precisamos gerar um DTB por variante de painel (o caminho que este
  documento propunha antes);
* basta publicar `dtbs/<base>.dtb` + `dtbs/overlays/mipi-panel*.dtbo` e deixar a
  entrada `extlinux.conf` apontar o overlay, igual à ROCKNIX.

O README da própria ROCKNIX avisa das limitações do parser: “*even a space after dtb
file path breaks the boot*” — `FDT` e `FDTOVERLAYS` precisam ser a última coisa da
linha, sem espaço sobrando.

### 9.3 Assinatura dos 5 overlays (medida nos arquivos)

| Overlay | `G` (tamanho/delays) | clock | modos | passos de init | terminador |
| --- | --- | --- | --- | --- | --- |
| `mipi-panel0` | 153x85 mm, `delays=20,20,20,120,20` | 30 MHz | **12** (640x480, porches variados) | 24 | termina em `I` (sem `#END`) |
| `mipi-panel1` | 52x70 mm, `20,150,20,120,20` | 29 MHz | 3 (iguais) | 25 | `#END` |
| `mipi-panel2` | 52x70 mm, idem | 29 MHz | 3 (iguais) | 187 | `#END` |
| `mipi-panel3` | 52x70 mm, idem | 29 MHz | 3 (iguais) | 188 | `#END` |
| **`mipi-panel4`** | 52x70 mm, idem | 29 MHz | 3 (**60/50/75** com porches recalculados) | **155** | `#END` |

`panel0` é claramente **outro painel** (153x85 mm e 12 modos de teste); `panel1..4` são
o mesmo painel físico com sequências de inicialização diferentes. É por isso que trocar
o overlay é o que resolve tela preta — e por isso `panel4` é o nosso.

### 9.5 Hardware do R36S (lido do DTB, não inferido)

| Item | Valor |
| --- | --- |
| Painel (base) | `gameconsole,r36s-panel`, `sitronix,st7703`; reset em **gpio3 pino 16**; `vdd`/`iovcc` = **LDO_REG8**; sem timings no DTB (driver) |
| Botões | `rocknix-singleadc-joypad`, nome `r36s_Gamepad`, **17 botões** + 2 analógicos por **multiplexador de ADC** (`amux-a` gpio3 p.11, `amux-b` gpio3 p.8, `amux-en` gpio3 p.13, `saradc` canal 1, `amux-count=4`) |
| Códigos | D-pad `0x220..0x223`, A `0x131`, B `0x130`, Y `0x134`, X `0x133`, L3 `0x13d`, R3 `0x13e`, FN `0x13c`, L1/L2 `0x136/0x137`, R1/R2 `0x138/0x139`, SELECT `0x13a`, START `0x13b` |
| Cartões | 2 slots SD: `mmc@ff370000` (cd gpio0 p.3) e `mmc@ff380000` (cd gpio3 p.14); **eMMC (`mmc@ff390000`) desligado** |
| USB | `dwc2` OTG com `usb-role-switch`, **default = host**, VBUS = `OTG_SWITCH` do rk817 |
| Áudio | `simple-audio-card` `rk817_int`, hp-det **gpio1 pino 22 (ativo alto)**, roteamento `Speaker -> SPKO` (**diferente da X55**, que usa HP) |
| Backlight | PWM1, período **25 µs**, 256 níveis, default 128 |
| Bateria | `simple-battery` 3380 mAh, 4,1 / 3,5 V |
| Detecção | nó `rocknix,device_switch` com `this = "r36s"` e os irmãos `r33s`/`rgb10x` |

### 9.6 O “escaneia e acha” existe — mas para o **aparelho**, não para o painel

O `APPEND` do extlinux tem `uboot.hwid_adc=${hwid_adc}`: o `boot.scr` da ROCKNIX lê
um **valor de ADC** no U-Boot, decide qual modelo é (r33s/r36s/rgb10x/…) e passa o
`hwid_adc` ao kernel. Se a leitura falhar (hardware raro), o próprio README manda
editar o `extlinux.conf` à mão — exatamente o que fizemos ao fixar `panel4`.
Continua valendo o que este documento diz: **não há detecção de painel**, só de placa.

### 9.7 O que ainda falta para gerar a nossa imagem

1. **Loader (U-Boot + blob de DDR) que inicializa este RK3326** — é o único item de
   peso. O caminho prático: o **nome/versão da imagem ROCKNIX** que funciona no
   aparelho; eu baixo do release e extraio `idbloader.img`/`u-boot.itb` (setores 64 e
   16384) e o `boot.scr`. Sem isso, qualquer U-Boot é chute (e o risco é a placa
   morrer sem print no serial).
2. **`boot.scr`** (ou `boot.ini`) da ROCKNIX — para ver como o `hwid_adc` é lido.
3. O `KERNEL` (`/KERNEL` no cartão) — só para conferir versão/config, não para usar.
4. Driver `rocknix-singleadc-joypad.c` + entrada do painel `gameconsole,r36s-panel`
   no `panel-sitronix-st7703.c`: ambos vêm do repositório da ROCKNIX (o CI já clona),
   falta conferir em que commit eles estão.

## 10. Duas linhas de CI: RK3566 continua sozinha, RK3326 tem a sua

O pedido foi separar as linhas e poder escolher o que construir na hora. Ficou assim:

| Arquivo | Placa | Quando roda |
| --- | --- | --- |
| `.github/workflows/build.yml` | **RK3566** (X55/X35S/X35H) | push na `main`, tags `v*`/`retroarch-*`, botão — **não foi alterado** |
| `.github/workflows/build-rk3326.yml` | **RK3326** (R35S/R36S) | **só** `workflow_dispatch` |

Como o de RK3326 não tem gatilho de push, ele não consome runner nem disputa
`concurrency` com a linha do RK3566.

### 10.1 O que se escolhe no *Run workflow*

| Entrada | Valores | O que faz |
| --- | --- | --- |
| `target` | `imagem` (padrão) / `loader` | `loader` constrói só o U-Boot mainline (teste isolado, cabe num cartão que já funciona). `imagem` constrói a imagem SD completa |
| `variant` | `kodi` (padrão) / `retroarch` | pacotes, overlay e serviço do `tty1` |
| `baudrate` | `1500000` (padrão) | console do U-Boot — o R36S usa 1500000 |

Com `target=imagem` o job encadeia: U-Boot `odroid-go2` → kernel v6.12 (+
`panel-generic-dsi.c` e `rocknix-singleadc-joypad.c` da ROCKNIX, commits fixos) →
DTB oficial do repositório + overlay `mipi-panel4` compilado com `dtc` → rootfs
Debian (debootstrap) → `build/build.sh game-console-r35s <variant>`.

### 10.2 O que o `create-image.sh` ganhou (compatível com o RK3566)

Três knobs por variável de ambiente, todas com o valor histórico como padrão —
sem elas, o comportamento do RK3566 é idêntico ao de antes:

| Variável | Padrão | Para quê |
| --- | --- | --- |
| `WALKMAN_EARLYCON` | `0xfe660000` | RK3326 usa **`0xff160000`** (uart2 muda de endereço entre os SoCs) |
| `WALKMAN_DTBS_GLOB` | `rk3566-powkiddy-*.dtb` | RK3326 usa `rk3326-*.dtb` |
| `WALKMAN_PANEL_OVERLAY_NAME` / `_FILE` | vazio | publica o `.dtbo` em `/overlays/` e escreve a linha `FDTOVERLAYS` no `extlinux.conf` |

### 10.3 Releases: todas as versões convivem

O job RK3326 publica com nome próprio — `rk3326-r36s-<variant>-sdcard.img.gz` +
o `.sha256` — no **mesmo** release da linha RK3566: tag vira o release da tag,
execução na `main` vira o `latest`. Como o nome do arquivo é distinto e o upload
usa `gh release upload --clobber` **por arquivo**, as imagens das duas
plataformas (e das duas variantes) acumulam em vez de se apagarem.

### 10.4 Ressalvas honestas

* A linha RK3326 **nunca rodou**: o YAML e o Python embutido foram validados
  localmente, mas o primeiro run vai revelar o que falta (é o padrão do projeto:
  o passo de build falha com mensagem clara em vez de gerar imagem quebrada).
* O kernel é o **v6.12 do projeto**, não o 7.1.2 da ROCKNIX: os dois drivers
  out-of-tree são os mesmos que a linha RK3566 já usa, mas `rocknix-singleadc-joypad.c`
  ainda não foi compilado contra 6.12 por ninguém.
* O DTB base é o **binário oficial** da ROCKNIX (copiado para `dts/`, sha256
  `b84245e6…`): não temos o `.dts` dele no mainline, e decompilar/reescrever só
  introduziria risco.

## 11. O loader mainline NÃO liga nesta placa (teste de 2026-10-30)

**Resultado medido no aparelho:** tela preta, **sem rede/USB**, nenhum sinal de
vida. Como o gadget USB só existe depois do kernel, isso mostra que **o kernel
nunca rodou** — a falha é antes dele.

O que foi gravado (imagem de teste, `sha256 488c4e55…`): a imagem oficial do
ROCKNIX **inteira**, com **apenas** os dois trechos do loader trocados:

| Offset | Conteúdo | Origem |
| --- | --- | --- |
| 32.768 (setor 64) | `idbloader.img` (120 KiB) | mainline binman: TPL com `px30_ddr_333MHz_v2.12.bin` + SPL |
| 8.388.608 (setor 16384) | `u-boot.itb` (1,1 MiB) | mainline `odroid-go2` + `px30_bl31_v1.37.elf` |

Primeiros 32 KiB (MBR) conferidos byte a byte com o original; a gravação foi
relida do arquivo e comparada.

### 11.1 O que isso (não) prova

* **Não prova** que o U-Boot mainline rodou. Sem console serial não há como
  separar (a) o TPL/DDR não inicializar a RAM de (b) o U-Boot subir e não
  conseguir bootar o `Image` cru pelo `extlinux`.
* **Prova** que o caminho "loader mainline + kernel" não chega a executar o
  kernel nesta placa.
* O defconfig tem `DEBUG_UART=y` em uart2 (`0xFF160000`): **se o SPL rodasse,
  imprimiria no serial** em 1500000. Sem serial, esse sinal se perde.

### 11.2 Hipótese principal

O `idbloader` do fabricante **não é rkbin** (começa com código, `3b 8c dc fc…`,
não com o magic `RK33`): a inicialização de DDR desta placa está no *miniloader*
da Rockchip, ajustada para o lote. O blob `px30_ddr_333MHz_v2.12.bin` é genérico
do SoC e pode não casar com o tipo/velocidade de DDR do R36S — se o treino falha,
o BootROM fica sem RAM e não há nem print. A outra candidata é o `px30_bl31`.

Para separar, o próximo teste **exige console serial** (`ttyS2`, 1500000 8N1):
* aparece `U-Boot 20xx…` → o loader funciona; o problema é o boot do kernel;
* nada aparece → é TPL/DDR/BL31, e aí a saída é o loader do fabricante (abaixo).

### 11.3 Decisão: o pipeline usa o loader oficial

`.github/workflows/build-rk3326.yml` ganhou a entrada **`loader`**:

| Valor | O que faz |
| --- | --- |
| `oficial` (**padrão**) | baixa `ROCKNIX-RK3326.aarch64-20261001-a.img.gz` (URL e sha256 `d693d2bb…` pinados), confere o checksum e extrai os **16 MiB iniciais**: `idbloader.img` = bytes 32 KiB..8 MiB, `u-boot.itb` = 8..16 MiB. É o loader que **liga** |
| `mainline` | constrói o U-Boot `odroid-go2` como antes (experimento; **não** liga hoje) |

O nome do asset passou a incluir o loader
(`rk3326-r36s-<variant>-<loader>-sdcard.img.gz`) para nunca confundir uma imagem
que liga com uma que não liga.

### 11.4 O que ainda daria para tentar no loader limpo

1. Console serial para ver se o SPL imprime (mais barato e decisivo).
2. U-Boot mainline com `CONFIG_BOOTCOMMAND` que ligue o **rockusb**/`ums` antes
   do `sysboot`: se o PC enxergar o dispositivo Rockchip, o loader está vivo —
   permite diagnosticar **sem** serial.
3. Extrair o `ddr.bin` do fabricante (está dentro do miniloader): exige
   engenharia reversa do formato `LOADER`; não vale antes do item 1.
