# Game Console R35S (RK3326) — painel, port e o que falta

Placa nova em preparação: **Game Console R35S** (a mesma base do R36S, vendida
como "Data Frog" e clones). Este documento existe porque essa placa **quebra a
premissa do repositório**: ela não é RK3566.

| Item | Estado |
| --- | --- |
| SoC | **Rockchip RK3326** (família PX30), 4x Cortex-A35, Mali-G31 — **confirmado** nos DTS de referência |
| DTS próprio no mainline | **não existe** (v6.12 tem 6 DTS `rk3326-*`, nenhum é R35S/R36S) |
| Painel | 640x480 DSI 4 lanes; **vários modelos** por lote — números em `devices/game-console-r35s/dts/Readme.md` |
| Overlay de painel | **gerado e validado** contra o overlay oficial `r36s-panel4` (160 strings idênticas) |
| Build no pipeline atual | **impossível**: U-Boot/kernel/blobs são RK3566 |
| Boot em hardware | **nunca testado** |
| Botões / ADC / bateria / Wi-Fi / BT | **não medidos** (nada foi inferido) |

## 1. O que já existia na pasta (antes de mexer)

O diretório `devices/game-console-r35s/` já estava no repositório com:

- `device.config` (nome errado, e o conteúdo era literalmente `1`) — trocado por
  `device.conf`;
- `dts/mipis-panel4.dts` e `dts/mipis-panel4-V22.dts` — **DTBs decompilados** de
  kernel de fabricante, com o painel completo (timings + sequência de init);
- `dts/Readme.md` e `uboot/README.md` vazios.

Ou seja: alguém já tinha ido atrás do **painel**, que é a parte que o R35S tem de
mais chato. Esse material é o que sustenta tudo aqui, e ele mostra, no primeiro
campo, que a placa é `rockchip,rk3326` e `arm,cortex-a35`.

## 2. Por que ela não entra no pipeline atual

O pipeline (`/.github/workflows/build.yml`) baixa U-Boot mainline, kernel v6.12 e
`rkbin`, e compila `powkiddy-x55-rk3566_defconfig` com `rk3568_bl31` +
`rk3566_ddr`. Para o R35S, os três pilares mudam:

| Peça | RK3566 (hoje) | RK3326 (R35S) | Fonte |
| --- | --- | --- | --- |
| Defconfig do U-Boot | `powkiddy-x55-rk3566` | `odroid-go2` (único rk3326 do mainline) | `doc/board/rockchip/rockchip.rst` |
| BL31 | `rk3568_bl31_v1.43.elf` | `px30_bl31_v1.37.elf` (rkbin **não** tem `rk3326_bl31`) | listagem de `rkbin/bin/rk33/` |
| DDR/TPL | `rk3566_ddr_1056MHz_*.bin` | `px30_ddr_333MHz_v2.12.bin` | idem |
| DTS | `rk3566-*.dts` | `rk3326-*.dts` (outro `Kconfig` de plataforma) | `arch/arm64/boot/dts/rockchip/Makefile` do v6.12 |
| Painel | `rocknix,generic-dsi` via DTS da X35S | 6 modelos diferentes → overlay | ver §3 |

Isso não é "ajuste de config": é um segundo alvo de build. Por isso
`device.conf` está com `image_dtb=` vazio (o empacotador recusa a placa em vez de
gerar uma imagem que não liga) e `status=reference-rk3326-needs-separate-pipeline`.

## 3. O painel: por que "escaneia e descobre" não existe (e o que usar)

### 3.1 O que a KNULLI faz (a recomendação que veio no pedido)

Fui ver o repositório da KNULLI. Para o R36S ela tem
`board/batocera/rockchip/rk3326/r36s/`, com kernel **4.4 de fabricante** e o DTB
**fixo** `rk3326-rg351mp-linux.dtb` copiado no boot (`create-boot-script.sh` +
`boot.ini`). Não há detecção de painel: a KNULLI escolheu o DTB da RG351MP
(640x480, mesma família de painel) e é isso.

### 3.2 O que a ROCKNIX/REG Linux (sucessora) faz

A wiki da REG Linux, na seção *New displays (R36s of year 2024)*, manda:

> "Determine which panel do you have (or just try every option until it works)"

e o mecanismo é um **overlay no cartão**: baixar
`mipi-panel.dtbo.r36s-panel*` do release
[`panel_overlays`](https://github.com/stolen/rnix/releases/tag/panel_overlays),
renomear para `overlays/mipi-panel.dtbo` na partição de boot, reiniciar. Os
overlays disponíveis hoje: `r36s-panel1`, `2`, `3`, `4`, `r36s_clone`,
`rg351mp-v2`, `rg351v-v2`, `cb408`.

### 3.3 Resumo honesto

**Nenhum firmware conhecido descobre o painel sozinho.** E não é preguiça: painel
DSI não tem EDID como monitor de PC, e sem driver de painel funcionando não há
como ler um identificador — o próprio driver é que precisa dos timings/init para
ligar a tela. O que existe é:

1. **escolher** (menu / arquivo), ou
2. **tentar as variantes** até uma ligar, ou
3. confiar no lote de fabricação (antes/meados/depois de 2024).

O que este projeto faz é o item 2 de forma organizada (§4).

## 4. Mecanismo adotado: overlay → um DTB por variante → entrada de boot

Reaproveita o que o projeto já usa para X35S/X55 (`extlinux.conf.<placa>` com
outro `FDT`), sem inventar suporte a overlay em tempo de boot:

```
dts/mipis-panel4.dts            <- DTS de fabricante (fonte)
        │  tools/panel_overlay_from_dts.py
        ▼
dts/panel-overlay/mipi-panel.dts   <- overlay rocknix,generic-dsi (gerado)
        │  dtc -@            (dtbo)  ou  fdtoverlay no DTB base
        ▼
dtbs/rk3326-<base>-panel4.dtb      <- uma imagem por variante de painel
        │
        └── extlinux/extlinux.conf.panel4  (FDT=...)
```

A ferramenta nova é `tools/panel_overlay_from_dts.py`. Ela não é chute: o formato
foi reconstruído e **conferido contra o overlay oficial**, e o teste embutido
compara string por string:

```sh
python3 tools/panel_overlay_from_dts.py \
    devices/game-console-r35s/dts/mipis-panel4.dts \
    --check-arquivo mipi-panel.dtbo.r36s-panel4     # -> OK: 160 strings idênticas
```

Três coisas que só apareceram por causa dessa comparação (e que, se feitas "no
olho", dariam tela preta):

1. **flags**: o fabricante usa `0xa03`, o overlay oficial usa **`0xe03`** — o
   driver `generic-dsi` espera o bit `MIPI_DSI_MODE_VIDEO` (0x400) ligado.
2. **`horizontal`/`vertical`**: são *(display, front-porch, sync-len,
   back-porch)*, **não** `hsync_start/hsync_end/htotal`. A tabela antiga em
   `docs/hardware-e-drivers.md` §4.1 está ambígua nesse ponto — os números
   oficiais (`640,46,2,44` para 640/46/2/44) não deixam dúvida.
   → **corrigido lá** (ver §7).
3. **50 Hz / 75 Hz**: no DTS do fabricante os dois estão com os porches do modo
   de 60 Hz (dão 77,4 fps). O overlay oficial recalcula o `vfront-porch` para
   bater no nome do nó. A regra está no script e é a única parte reconstruída com
   **um** ponto de dados — está marcada como hipótese no cabeçalho dele.

## 5. O que o pipeline precisa (checklist para o próximo build RK3326)

Nada disso foi feito — é a lista de trabalho, na ordem:

1. **Novo job/arquivo de workflow para RK3326** (não misturar com o job atual):
   `make odroid-go2_defconfig`, `BL31=px30_bl31_v1.37.elf`,
   `ROCKCHIP_TPL=px30_ddr_333MHz_v2.12.bin`.
2. **Kernel**: `ARCH_PX30`, os drivers de `devices/game-console-r35s/kernel.fragment`
   e o `panel-generic-dsi.c` da ROCKNIX (o CI já sabe buscá-lo — passo
   "Fetch ROCKNIX Config & Patches").
3. **DTB base**: o R35S não tem DTS no mainline. Candidatos, do mais provável ao
   menos, para bring-up:
   `rk3326-anbernic-rg351m` (640x480, `elida,kd35t133`, mesma faixa de hardware
   que a KNULLI escolhe para o R36S) → `rk3326-gameforce-chi` → `rk3326-odroid-go3`.
   **Nenhum é o R35S**: botões e ADC vão precisar de DTS próprio, medido no
   aparelho. Não escrever `gpio-keys` por chute.
4. **Overlay do painel**: compilar `dtc -@` e aplicar com
   `fdtoverlay -i <base>.dtb -o <base>-panel4.dtb mipi-panel.dtbo`, gerando uma
   entrada `extlinux.conf.panel<N>` por variante.
5. **Rotação**: `display_transform` em `device.conf` já é lido pelo
   `build/create-image.sh`; hoje está `normal` (painel 640x480 na horizontal),
   **não medido**.
6. **Rootfs**: igual ao das outras placas (Debian + Kodi/RetroArch). O rootfs não
   depende do SoC.

## 6. Riscos e pontos cegos (o que pode dar errado sem aviso)

| Risco | Por quê | Como detectar |
| --- | --- | --- |
| **Blob de DDR** | o `px30_ddr_333MHz` é do Go Advance; o R35S tem outro lote de memória. Se errar, o U-Boot morre sem print | sem serial, é tela preta sem nada; com serial (`ttyS2`, 1500000n8), nada aparece |
| **Botões/ADC** | DTS base é de outra placa | `evtest` / `/proc/bus/input/devices` |
| **Wi-Fi/BT** | não se sabe se o R35S tem rádio nem qual | `dmesg | grep -iE 'mmc|rtw|hci'`, `rfkill list` |
| **Áudio** | o DTS base usa `rk817-codec`; o R35S deve usar o mesmo, mas o caminho do amplificador é placa | `aplay -l`, `dmesg | grep -i asoc` |
| **TF1/TF2** | o R35S tem dois slots; o Go Advance só um | `lsblk`, `dmesg | grep mmc` |
| **USB-C** | o R35S usa USB-C; papel OTG/UDC desconhecido | `ls /sys/class/udc`, `dmesg | grep -i dwc` |

## 7. Correção de documentação feita junto

`docs/hardware-e-drivers.md` §4.1 dizia que `horizontal`/`vertical` eram
`hdisplay, hsync_start, hsync_end, htotal`. A comparação com o overlay oficial
mostra que o campo é *(display, front-porch, sync-len, back-porch)*. O texto foi
corrigido; os valores da X35S que estão lá continuam válidos (eles já eram
porches, só estavam descritos com o nome errado).

## 8. Próximos passos (na ordem)

1. **Ligar o aparelho com a imagem oficial (ROCKNIX/ArkOS) e medir**, antes de
   escrever qualquer DTS nosso:
   - `cat /proc/device-tree/model` e `cat /proc/device-tree/compatible`;
   - qual DTB a imagem oficial usa (`ls /boot`, `cat /boot/extlinux/extlinux.conf`
     ou `boot.ini`);
   - `ls /sys/bus/iio/devices/` (eixos por ADC), `evtest` (botões),
     `lsblk` (TF1/TF2), `ls /sys/class/udc` (USB), `rfkill list` (rádio).
   Isso responde "qual DTB base" e "quais botões" com fato, não com palpite.
2. Se a tela ficar preta: **é o painel** (não o resto). Trocar a variante
   (`panel1`…`panel4`, `r36s_clone`) até ligar; anotar qual.
3. Só então montar o job RK3326 no CI (checklist §5) e gerar a primeira imagem.
4. Com a imagem no aparelho: `dmesg` completo para `diagnostico.txt`, como já é
   feito nas outras placas.
